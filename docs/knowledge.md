### 3.工具定义

一个工具由三个部分组成
- description：工具作用，用于模型判断什么时候调用它，是给模型看得
- inputSchema：工具接受的参数类型
- execute：实际执行函数
工具的 description 和 inputSchema 里的属性 description，本质上就是在写 prompt。

### 4.SDK自动循环

提供了一个自动多部执行的能力`stopWhen`，模型返回工具调用的时候，SDK自动执行，把结果喂回模型，直至模型不再调用工具为止
- stopWhen: stepCountIs(5), // 最多跑 5 步
- 模型最多可以进行 5 轮"思考→调用工具→拿到结果→继续"的循环。如果 5 步之后模型还在调用工具，强制停止。

### 5.工具调用死循环怎么检测

常见模式：
- 通用重复，相同的工具+参数，调用了多次
- 乒乓重复，A,B工具循环调用，停不下来
- 轮询无进展，不断轮询poll检查状态，始终无进展

解决：指纹+滑动窗口
- 工具名+参数做确定的JSON序列化，key排序，无论参数如何变化，指纹都一样
- 滑动窗口，仅仅维护最近30条
- 只有调用指纹和结果指纹都一样，才算没进展

检测到重复之后，不能一刀切，三级预警
先给模型提示---再阻断工具调用---最后全局熔断，强制停止

### 16.TTL时间衰减

前面两条截断和总量预算（调用越早的工具越有限被简短标记）=》基于空间维度上的

时间衰减=>时间维度上
工具结果的价值随着时间而快速衰退，但不能立刻删掉（因为后面的回复也能用到了，删掉会导致对话结构破坏）

TTL修剪---只修剪 tool 结果，user/assistant 消息永不修剪
- 5分钟的，保留头部和尾部，但是中间的大段内容不再占用空间了
- 10分钟的，直接删掉，只保留发生过什么事，内容全部清除


**保留错误经验**，让模型知道，这条路之前走过，走不通
TTL 修剪前先检查工具结果是否包含 error、失败、不存在 等错误关键词，命中的直接跳过不修剪。

### 19.什么该记，什么不用

记得越多，模型的注意力越差，检索的噪音越大
记忆是线索，不是事实——使用前先验证其准确性

- 排除法
- 能从代码推导的不记
- git log里有的不记
- 文档里有的不记
- 只存在于对话中，无法从其他地方获取的

- 村什么
- 用户画像：角色、偏好、技术背景、工作习惯
- 行为反馈：用户对agent行为的纠正和确认，让他知道什么该做，什么不能做
- 项目动态：进行种的工作，决策，截止日期（具体点
- 外部资源：索引，或者记录位置

### 20.记忆会变坏，因此需要维护

- 记忆污染：把推测当成事实
Agent 看到旧的 MySQL 配置文件就存下"项目用 MySQL"，实际上早迁到 PostgreSQL 了。
- 爆炸——只存不删，信噪比越来越低。
500 条记忆里挑 5 条相关的，搜出来基本没用。
- 过期——代码变了记忆没跟上。
这是最隐蔽也最危险的——Agent 不会怀疑自己的记忆，它会基于错误信息做出自信的错误决策。
- 冲突——新旧记忆互相矛盾

### 21.记忆污染---源头控制，一开始就不让垃圾进来

能从其他地方推导出来的信息不存
这些信息都有权威来源——代码本身就是，git 本身就是

该存的：只存在于对话中、其他地方推导不出来的——用户偏好、纠正反馈、项目决策、外部资源引用。

### 25.飞书长连接和webhook之间是什么关系

两者解决的是同一件事，飞书把（用户发消息）这件事送到你的程序里

长连接：官方SDK帮你封装好的websocket，是websocket的一种产品化叫法，不用自己写ws库，也不管握手细节，WSClient 一行 start() 全托管了

- webhook
你在飞书的后台配一个公网HTTPS地址
用户发消息，飞书主动POST事件JSON到你的地址
你的服务要有公网 IP/域名、HTTPS 证书、签名验签、可能还要 ngrok 内网穿透
适合生产环境

- 长连接模式
你的程序启动，主动连接飞书
飞书 后面有事件，顺着这个websocket退下来，不需要ip域名等
适合本地开发

### 27.subAgent

核心价值是：用独立的上下文做探索，压缩后回传结论，父agent的上下文保持干净

给了派生子agent的工具，模型不一定用
其实 function calling 本身就是最自然的意图检测机制。模型看到工具描述后自行决定调哪个——这和"意图检测"是一回事，只不过检测器是模型自身的推理能力。所以最有效的做法是把工具描述写清楚：在 spawn_agent 的 description 里明确适用场景（"多项独立调研任务、需要并行对比时使用"），同时在 system prompt 里加一句引导（"涉及多个独立目标的调研、对比任务时，优先用 spawn_agent 并行执行"）。这两层加上去，主流模型的命中率已经很高了。

### 28.子agent隔离的本质

本项目采用同进程隔离
直接就是子和父采用不同的msg数组，独立的，不同fork子进程
常见的还有git worktree和进程级的隔离

隔离就是一个空的 messages 数组：子 Agent 从零开始，不继承父 Agent 的对话历史
结果只取最后一条 assistant 消息：几万 token 的探索过程压缩成几百 token 的结论
**Promise.all 做并行：多个子 Agent 同时执行，总耗时等于最慢的那个
两道保护机制：深度限制防递归、并发限制防资源耗尽
同进程隔离**：零开销、启动快，可以覆盖大部分场景
